# Offline TAKI — Phase 1: Architecture

Status: proposal for review. Nothing in this document is implemented yet.
Date: 2026-09-24
Scope: an offline, nearby-multiplayer TAKI-style card game. Android is the first target
and ships as a standalone APK. iOS comes later behind the same abstractions.

---

## 0. Decisions at a glance

| Topic | Decision | Why (short) |
|---|---|---|
| Framework | React Native (bare, community CLI), TypeScript, Hermes | Standard Gradle project, first-class Kotlin native modules, engine and protocol in plain TypeScript, matches your existing React/TS stack |
| Android↔Android transport (MVP) | Google Nearby Connections, `P2P_STAR` | Purpose-built for offline nearby, automatic discovery, encrypted, no pairing dialogs, handles Bluetooth/Wi‑Fi internally |
| Android↔iPhone transport (later) | Bluetooth Low Energy GATT (custom, both platforms) | The only config-free, offline path that both OSes expose to third-party apps today |
| iPhone↔iPhone transport (later, optional) | Multipeer Connectivity, or reuse BLE GATT | Apple's native offline P2P |
| Topology | Star: one host device owns the authoritative state | Matches Nearby's `P2P_STAR`, matches the host-authoritative requirement |
| Sync model | Event log with a monotonically increasing `stateVersion`; snapshots on join, reconnect or gap | Simple, deterministic, cheap on low-bandwidth links |
| Privacy | Host projects a per-player view; other hands never leave the host | Requirement |
| Encoding on the wire | UTF‑8 JSON, validated with zod on receipt | Debuggable, tiny messages, easy to swap to CBOR later |
| Persistence | AsyncStorage: player name, settings, last session (gameId, playerId, reconnect token) | No account, survives app restart |
| Build output | `android/app/build/outputs/apk/release/app-release.apk` via `gradlew assembleRelease` | Standalone, Hermes bytecode bundled, no Metro |

## 1. Mobile framework

### Recommendation: React Native (bare), TypeScript

Concretely: a project generated by `@react-native-community/cli` (not Expo Go, not Expo managed),
with the `android/` folder committed, one custom Kotlin native module for nearby networking,
Hermes enabled, New Architecture enabled (default in current RN).

Reasons, in order of weight:

1. **Native module control.** Nearby Connections (now) and BLE GATT (later) both need custom
   Kotlin/Swift. A bare RN project is a normal Android Gradle project. Manifest, Gradle,
   `MainApplication`, permissions and a foreground service are all edited directly, which is
   exactly what your build requirement asks for.
2. **Standalone APK is the normal release path.** `gradlew assembleRelease` runs the JS bundler,
   compiles the bundle to Hermes bytecode, and embeds it in the APK. Metro is only a dev-time tool.
3. **The game engine, protocol and host/client logic are plain TypeScript** with no React or
   React Native imports. They run and are tested under Jest on Node. The same modules run on the
   host and on clients, so legal-move highlighting on a client uses the same code the host uses to
   validate.
4. **Your other work is React/TypeScript.** The UI, hooks and state code will feel familiar; the
   only foreign code is a few hundred lines of Kotlin (and later Swift).

### Why not Flutter

Flutter is a legitimate choice and I want to be fair to it:

- `flutter build apk --release` is slightly simpler than the RN Gradle flow.
- The Flutter `nearby_connections` plugin already wraps Google Nearby Connections on Android, and
  `bluetooth_low_energy` supports BLE *peripheral* mode on both platforms, which the RN ecosystem
  lacks as a maintained package.
- Dart 3 sealed classes are excellent for the state machine and message unions.

It loses on one point that matters more for you: the whole team would work in Dart instead of
TypeScript, and the native module work is small enough (roughly 300–500 lines of Kotlin for the
Nearby transport) that ecosystem plugins are not the deciding factor. If you were Dart-fluent I
would call this close to a coin flip.

### Why not Expo managed

Expo "prebuild" would also produce a standard Gradle project, but the two constraints you set
("do not depend on Expo Go", "do not pick Expo if it complicates native networking") are best met
by owning `android/` outright. We lose nothing we need.

### Windows development note

Android builds run fine on Windows (JDK 17, Android SDK, Gradle). iOS builds later require macOS
or a cloud build service; that is a Phase 7 concern and does not affect the Android MVP.
Bluetooth/Nearby do not work in emulators, so all networking testing is on physical phones.

## 2. Offline nearby networking

### 2.1 Requirements recap

- No internet, no server, no account, works in airplane mode once the user re-enables the radio.
- UX is two buttons: Create Game / Join Nearby Game. No IPs, ports, SSIDs, or pairing dialogs.
- 2–8 players on their own phones, seated within a few metres.
- Messages are tiny: a game action is under 200 bytes; a full per-player snapshot for 8 players
  is under 2 KB. Bandwidth is not a constraint. Latency under ~300 ms is fine for a card game.

### 2.2 Technology evaluation

| Technology | Android | iOS | Android↔iOS | Auto discovery | User config | Offline | Bandwidth | Notes |
|---|---|---|---|---|---|---|---|---|
| **Google Nearby Connections** | Yes | Beta SDK exists, limited | Not reliable | Yes | None | Yes (needs Play Services installed, not internet) | High (upgrades to Wi‑Fi) | Best Android↔Android option. Missing on Huawei/de-Googled phones |
| **Apple Multipeer Connectivity** | No | Yes | No | Yes | None | Yes | High (AWDL) | Best iPhone↔iPhone option. Proprietary link layer |
| **Bluetooth Low Energy (GATT)** | Central + peripheral (peripheral optional on some phones) | Central + peripheral | **Yes** | Yes (service UUID) | None (no pairing needed) | Yes | Low (~5–20 KB/s) but enough | Only truly cross-platform path today. Host is the GATT server; practical cap 6–7 clients |
| Bluetooth Classic (RFCOMM) | Yes | Third-party apps: no | No | Yes | Pairing dialog unless insecure RFCOMM | Yes | Medium | Nearby Connections uses it internally; not useful directly |
| Wi‑Fi Direct (P2P) | Yes | Only as a "legacy" client if it knows the passphrase | Partial | Android only | Passphrase must be exchanged out of band | Yes | High | Useful only as a bandwidth upgrade behind BLE |
| Local-only hotspot (Android) + BLE credential handoff | Android host only | Joins via `NEHotspotConfigurationManager` (system confirm dialog) | Yes, Android host only | Via BLE | One system dialog | Yes | High | Viable fallback; iPhone cannot host a hotspot without cellular |
| Wi‑Fi Aware (NAN) | API 26+, hardware-dependent | iOS 26+ framework, newer iPhones only | In principle yes (standard) | Yes | Pairing UI on iOS | Yes | High | Promising but device support is patchy. Needs a spike; not for the MVP |
| Airplane / venue Wi‑Fi LAN + mDNS + TCP | Yes | Yes | Yes | mDNS if allowed | Must join the network | Usually blocked by client isolation | High | Nice-to-have at home, unreliable on planes |
| Any cloud relay (Firebase, WebSockets, etc.) | — | — | — | — | — | **No** | — | Excluded by requirement |

### 2.3 Can devices discover each other automatically? Honest matrix

| Pair | Automatic discovery + connection, fully offline | Transport | Phase |
|---|---|---|---|
| Android ↔ Android | **Yes** | Nearby Connections | Phase 2 (MVP) |
| Android ↔ Android, no Google Play Services | Yes | BLE GATT | Later |
| iPhone ↔ iPhone | **Yes** | Multipeer Connectivity (or BLE GATT) | Later |
| Android ↔ iPhone | **Yes, with caveats** | BLE GATT only | Later |
| Android ↔ iPhone | Experimental | Wi‑Fi Aware (iOS 26+, NAN-capable Android) | Spike |
| Android host, iPhone clients | Yes, one system dialog per iPhone | Android hotspot + BLE credential handoff | Fallback if BLE proves too slow |

Caveats for Android ↔ iPhone over BLE:

- Nearby Connections and Multipeer Connectivity **do not interoperate**. A mixed table must be
  hosted over BLE GATT, so that transport must exist on both platforms before mixed play works.
- Throughput is low but sufficient for this game. Expect 100–300 ms per message hop.
- The host is a GATT server with one connection per client. Android peripheral mode supports
  roughly 7 concurrent centrals; plan for 2–6 clients over BLE, 8 in the protocol.
- Some cheaper Android phones cannot act as a BLE peripheral. They can join but not host; the app
  detects this and tells the user.
- An iOS host must stay in the foreground while people are joining (iOS strips service UUIDs from
  background advertisements in a way Android scanners cannot filter on). Existing connections
  survive backgrounding with the `bluetooth-peripheral` background mode.

### 2.4 Recommendation

**Phase 2 (Android MVP): Google Nearby Connections with `Strategy.P2P_STAR`.**

- Host calls `startAdvertising`; joiners call `startDiscovery`. Discovery uses BLE and Bluetooth
  Classic, so it works with only Bluetooth re-enabled in airplane mode. If Wi‑Fi is also on,
  Nearby may upgrade the link to Wi‑Fi Direct/hotspot for bandwidth; we disable "disruptive"
  upgrades so it never disconnects the phone from a network the user chose.
- The link is encrypted by Nearby and offers a verification token we can show as a join code.
- Payloads of type `BYTES` (up to 32 KB) are delivered reliably and in order per endpoint. No
  fragmentation code on our side.
- Runs entirely inside Google Play Services on the device. It does not contact the internet.

**Later: BLE GATT transport, on Android and iOS, behind the same interface.** This is what makes
Android↔iPhone and Play-Services-free Android work. It is more code (fragmentation, MTU handling,
Android BLE quirks), which is why it is not the first transport.

**Optional later: Multipeer Connectivity** for iPhone-only tables if BLE feels slow there.

At "Create Game" the host chooses (or the app auto-selects) which transport to advertise on. The
lobby, protocol, engine and UI do not know which one is in use.

### 2.5 What I ruled out and why

- **Classic Bluetooth sockets**: no cross-platform story, pairing dialogs, and Nearby already uses
  them internally with a better API.
- **Wi‑Fi Direct as the primary**: Android-only group formation, requires location permission,
  and the iPhone side needs a passphrase handoff anyway. Nearby already uses it as an upgrade.
- **Asking users to join a hotspot manually**: violates the "no configuration" requirement.
- **Google's iOS Nearby Connections SDK**: exists as an open-source beta but its medium support
  and Android interop are not something I would bet the product on without a spike. Worth a
  time-boxed test later.
- **Cloud relays**: excluded by requirement, and they would not work on a plane anyway.

## 3. Android implementation (MVP)

### 3.1 Nearby Connections flow

```
Host (Phone A)                                  Client (Phone B)
--------------                                  ----------------
startAdvertising(endpointName, SERVICE_ID,
   lifecycleCallback, P2P_STAR)
                                                startDiscovery(SERVICE_ID, discoveryCallback, P2P_STAR)
                                                onEndpointFound(endpointId, info.endpointName)
                                                   -> decode advertisement, show in "Nearby games" list
                                                user taps game
                                                requestConnection(localName, endpointId, lifecycleCallback)
onConnectionInitiated(endpointId, info)         onConnectionInitiated(endpointId, info)
   acceptConnection(endpointId, payloadCb)         acceptConnection(endpointId, payloadCb)
onConnectionResult(endpointId, OK)              onConnectionResult(endpointId, OK)
                                                stopDiscovery()
                                                sendPayload(endpointId, JOIN_REQUEST)
onPayloadReceived -> protocol layer
sendPayload(endpointId, JOIN_ACCEPTED / JOIN_PENDING / JOIN_REJECTED)
...
onDisconnected(endpointId) -> protocol layer marks player disconnected
```

Design choices:

- `SERVICE_ID` is a constant string unique to this app (e.g. `global.ultra.offlinetaki.v1`). Only
  this app's instances see each other.
- `endpointName` carries a compact advertisement: protocol version, short game id, game name,
  host name, player count / max, "code required" flag. Keep it under ~100 bytes.
- The transport **always accepts** the Nearby connection immediately. Host approval and join
  codes live in the protocol layer (`JOIN_REQUEST` → `JOIN_ACCEPTED`/`JOIN_PENDING`/`JOIN_REJECTED`).
  This keeps behaviour identical across Nearby, BLE and Multipeer, where link-level acceptance is
  not available or differs.
- Nearby's `authenticationDigits` are surfaced in the `peerConnected` event as an optional
  verification code, shown in the lobby for a visual sanity check.
- Host keeps advertising until the game starts (or the lobby is full), then stops advertising.
  Host restarts advertising when the game is running with a disconnected seat, so a rejoining
  player can find it.

### 3.2 Native module: `NearbyConnectionsModule` (Kotlin)

Location: `android/app/src/main/java/global/ultra/offlinetaki/nearby/`.
A React Native TurboModule (codegen spec in `src/native/specs/NativeNearbyConnections.ts`)
exposing:

| Method | Purpose |
|---|---|
| `getCapabilities()` | Play Services available, Bluetooth available, max peers |
| `getRadioState()` | Bluetooth on/off, Wi‑Fi on/off, Location services on/off |
| `startAdvertising(advertJson)` / `updateAdvertising` / `stopAdvertising` | Host role |
| `startDiscovery()` / `stopDiscovery()` | Client role |
| `connect(endpointId, timeoutMs)` | Client role |
| `send(endpointId, payloadString)` | Both; UTF‑8 → `Payload.fromBytes` |
| `disconnect(endpointId)` / `shutdown()` | Cleanup; `stopAllEndpoints()` |
| `startHostService(title)` / `stopHostService()` | Foreground service to keep the host alive |
| `setKeepScreenOn(bool)` | `FLAG_KEEP_SCREEN_ON` during a game |
| `openAppSettings()` / `openBluetoothSettings()` / `openLocationSettings()` | Recovery UX |

Events (via `RCTDeviceEventEmitter`): `radioState`, `gameFound`, `gameLost`, `peerConnected`,
`peerDisconnected`, `message`, `error`.

Everything above the module is TypeScript. The module does not know what a card is.

### 3.3 Permissions by Android version

Declared in `AndroidManifest.xml` (from Google's Nearby Connections documentation):

| Permission | Versions | Runtime prompt | Why |
|---|---|---|---|
| `BLUETOOTH`, `BLUETOOTH_ADMIN` | ≤ Android 11 (`maxSdkVersion="30"`) | No | Legacy Bluetooth |
| `ACCESS_WIFI_STATE`, `CHANGE_WIFI_STATE` | all | No | Wi‑Fi mediums |
| `ACCESS_COARSE_LOCATION` | ≤ Android 9 (`maxSdkVersion="28"`) | Yes | Legacy scan requirement |
| `ACCESS_FINE_LOCATION` | ≤ Android 12L (`maxSdkVersion="32"`) | Yes | Bluetooth/Wi‑Fi scanning requirement |
| `BLUETOOTH_SCAN` (`neverForLocation`), `BLUETOOTH_ADVERTISE`, `BLUETOOTH_CONNECT` | Android 12+ | Yes | Modern Bluetooth permissions |
| `NEARBY_WIFI_DEVICES` (`neverForLocation`) | Android 13+ | Yes | Wi‑Fi Direct/Aware without location |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE` | Android 9+ / 14+ | No | Keep the host alive with the screen off |
| `POST_NOTIFICATIONS` | Android 13+ | Yes (optional) | Show the "Hosting" notification |

What the user sees at runtime:

- Android 13+: one "Nearby devices" dialog (covers Bluetooth and Wi‑Fi nearby permissions) and
  optionally a notifications dialog. No location.
- Android 12: "Nearby devices" plus "Location" dialogs.
- Android 6–11: "Location" dialog, **and the system Location toggle must be on** for discovery.
  The app detects this and shows a one-tap link to the setting. GPS works in airplane mode, so
  this does not conflict with flying.

Also required: Bluetooth turned on. The app requests it with `ACTION_REQUEST_ENABLE` (system
dialog) or links to settings.

### 3.4 Manifest, Gradle and application changes

- `android/app/build.gradle`: `implementation "com.google.android.gms:play-services-nearby:19.3.0"`
  (19.5.0 ships Kotlin 2.4 metadata that React Native 0.87's Kotlin 2.2 toolchain cannot read;
  bump the two together).
- `AndroidManifest.xml`: permissions above; `<uses-feature android:name="android.hardware.bluetooth_le" android:required="true"/>`;
  `<service android:name=".nearby.HostForegroundService" android:foregroundServiceType="connectedDevice" android:exported="false"/>`.
- `MainApplication.kt`: register `NearbyConnectionsPackage` in `getPackages()`.
- `MainActivity.kt`: no changes expected beyond the template.
- Release manifest overlay (`src/release/AndroidManifest.xml`): optionally remove the `INTERNET`
  permission that the RN template adds for Metro. This is the strongest possible proof the release
  APK cannot reach the internet. To be verified in Phase 2 that Nearby still works without it
  (it should: Nearby's networking runs inside Play Services).
- ProGuard/R8 in release: Play Services ships its own consumer rules; the RN template's rules
  cover Hermes. No custom rules expected.

### 3.5 Keeping the host alive

- **Foreground service** on the host with a "Hosting Ofir's Game" notification. Without it,
  Android may suspend the app when the screen is off and the Nearby callbacks stop arriving.
- **Screen stays on** during a game on all devices (`FLAG_KEEP_SCREEN_ON`), toggled off in menus.
- Clients that background and return trigger a reconnect through the protocol layer.

### 3.6 Known Nearby Connections quirks to design around

- Practical concurrent-connection ceiling over Bluetooth is roughly 4–6 clients; Wi‑Fi upgrade
  raises it. Recommend advertising up to 8 seats but expect real tables of 2–6.
- Nearby temporarily renames the Bluetooth adapter to encode advertising data and restores it
  later. Harmless, but users may notice in Bluetooth settings.
- Discovery restarted too often gets throttled by the OS. The client discovers only while the
  Join screen is open.
- Play Services absent (Huawei, some Chinese ROMs, de-Googled phones): detect with
  `GoogleApiAvailability`, show a clear message. The BLE GATT transport removes this limitation later.
- OEM battery killers (Xiaomi, Oppo, etc.) may still kill the app; the foreground service and a
  "keep the app open" hint in the lobby mitigate it.

### 3.7 Later: BLE GATT transport on Android (for iOS interop)

Same TypeScript interface, second Kotlin module:

- Host: `BluetoothLeAdvertiser` advertising a 128-bit service UUID; `BluetoothGattServer` with
  three characteristics: `GAME_INFO` (read), `C2H` (write), `H2C` (notify). Per-client send queue
  gated on `onNotificationSent`. MTU tracked per device via `onMtuChanged`.
- Client: filtered `BluetoothLeScanner` scan, `connectGatt(..., TRANSPORT_LE)`, `requestMtu(517)`,
  enable notifications via the CCCD descriptor, `requestConnectionPriority(HIGH)` during play.
- Fragmentation in native code: 3-byte header (message counter, chunk index, chunk count) so JS
  sees whole messages.
- Retry on GATT status 133, always `close()` the GATT, serialize GATT operations.

## 4. iOS implementation (deferred, design only)

- **BLE GATT transport** in Swift with CoreBluetooth. Host: `CBPeripheralManager` with the same
  UUIDs, `updateValue(_:for:onSubscribedCentrals:)` with back-pressure via
  `peripheralManagerIsReady`. Client: `CBCentralManager` filtered scan, `setNotifyValue`,
  `writeValue(.withResponse)`, `maximumWriteValueLength`. Info.plist:
  `NSBluetoothAlwaysUsageDescription`. Background modes: `bluetooth-central`, `bluetooth-peripheral`.
  No location permission needed on iOS for BLE.
- **Multipeer Connectivity** (optional, iPhone-only tables): `MCNearbyServiceAdvertiser` /
  `MCNearbyServiceBrowser` / `MCSession` with `encryptionPreference = .required`. Info.plist:
  `NSLocalNetworkUsageDescription` and `NSBonjourServices` (`_offlinetaki._tcp`, `_offlinetaki._udp`).
  Works over peer-to-peer Wi‑Fi (AWDL) with Wi‑Fi enabled but not connected, so airplane mode +
  Wi‑Fi on is fine.
- Exposed to JS as a TurboModule implementing the same spec as the Android module.
- iOS builds require macOS or a cloud build. Not part of the Android MVP.

## 5. Cross-platform limitations summary

1. Same-platform native stacks (Nearby, Multipeer) are excellent but mutually incompatible.
2. Mixed tables require BLE GATT on both sides; slower, fewer seats, host must be a phone that
   supports BLE peripheral mode.
3. An iPhone cannot host a Wi‑Fi hotspot without cellular, so any Wi‑Fi-based mixed fallback
   requires an Android host.
4. Wi‑Fi Aware is the standards-based future for mixed Wi‑Fi P2P (iOS 26+), but device support
   and iOS pairing UX need a spike before relying on it.
5. Nearby Connections needs Google Play Services on the device (offline is fine).
6. Both platforms remember that you re-enabled Bluetooth in airplane mode, but the app must
   detect "radio off" and guide the user, since neither OS lets an app silently turn Bluetooth on.

## 6. Host/client architecture

### 6.1 Layers

```
┌──────────────────────────── UI (React Native) ────────────────────────────┐
│ screens/Home  screens/Lobby  screens/Game        components/  hooks/       │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ observes ClientGameView, dispatches intents
┌───────────────────────────────▼────────────────────────────────────────────┐
│ networking/client: GameClient  (runs on EVERY device, including the host) │
│   connection FSM · JOIN handshake · applies GAME_EVENTs in version order    │
│   detects gaps → RESYNC_REQUEST · stores reconnect token                    │
└───────────────────────────────┬────────────────────────────────────────────┘
                                │ protocol messages (JSON)
┌───────────────────────────────▼────────────────────────────────────────────┐
│ networking/host: GameHost  (runs ONLY on the host device)                  │
│   PeerHub (transport peers ↔ playerIds) · Lobby · action validation         │
│   EventLog (versioned) · PlayerViewProjector (privacy) · heartbeats         │
└───────────────┬───────────────────────────────────────────┬────────────────┘
                │ pure function calls                       │ bytes
┌───────────────▼───────────────┐             ┌─────────────▼─────────────────┐
│ game/engine (pure TypeScript) │             │ networking/transport           │
│ reduce(state, action) →       │             │ NearbyTransport interface      │
│   {state', events[]}          │             │  ├ NearbyConnectionsTransport  │
│ legalMoves(state, playerId)   │             │  ├ BleGattTransport (later)    │
│ project(state, viewerId)      │             │  ├ LoopbackTransport (host UI) │
│ No React, no RN, no network   │             │  └ MemoryTransport (tests)     │
└───────────────────────────────┘             └────────────────────────────────┘
```

Key idea: **the host's own UI is just another client**, connected to `GameHost` through an
in-process `LoopbackTransport`. UI code is identical on every phone; the host phone simply also
runs `GameHost`.

### 6.2 Transport abstraction

```ts
// networking/transport/NearbyTransport.ts
export type PeerId = string;                 // Nearby endpointId, BLE address, "loopback"

export enum TransportKind {
  NearbyConnections = 'nearby-connections',
  BleGatt = 'ble-gatt',
  Multipeer = 'multipeer',
  Loopback = 'loopback',
  Memory = 'memory',
}

export enum RadioState { Ready = 'ready', BluetoothOff = 'bluetooth-off',
  LocationOff = 'location-off', PermissionDenied = 'permission-denied',
  Unsupported = 'unsupported' }

export interface GameAdvertisement {
  protocolVersion: number;
  gameId: string;
  gameName: string;
  hostName: string;
  playerCount: number;
  maxPlayers: number;
  requiresJoinCode: boolean;
}

export interface DiscoveredGame extends GameAdvertisement {
  peerId: PeerId;
  transport: TransportKind;
  lastSeenAt: number;
}

export interface TransportCapabilities {
  kind: TransportKind;
  canHost: boolean;
  maxPeers: number;
  maxMessageBytes: number;
}

export type TransportEvent =
  | { type: 'radioState'; state: RadioState }
  | { type: 'gameFound'; game: DiscoveredGame }
  | { type: 'gameLost'; peerId: PeerId }
  | { type: 'peerConnected'; peerId: PeerId; verificationCode?: string }
  | { type: 'peerDisconnected'; peerId: PeerId; reason: 'remote' | 'local' | 'timeout' | 'radio' }
  | { type: 'message'; peerId: PeerId; payload: string }
  | { type: 'error'; code: string; message: string };

export interface NearbyTransport {
  readonly capabilities: TransportCapabilities;
  getRadioState(): Promise<RadioState>;

  // host role
  startAdvertising(ad: GameAdvertisement): Promise<void>;
  updateAdvertising(ad: GameAdvertisement): Promise<void>;
  stopAdvertising(): Promise<void>;

  // client role
  startDiscovery(): Promise<void>;
  stopDiscovery(): Promise<void>;
  connect(peerId: PeerId, opts?: { timeoutMs?: number }): Promise<void>;

  // both roles
  send(peerId: PeerId, payload: string): Promise<void>;   // whole message; ordered per peer
  disconnect(peerId: PeerId): Promise<void>;
  shutdown(): Promise<void>;
  subscribe(listener: (event: TransportEvent) => void): () => void;
}
```

Differences from the sketch in the brief, and why:

- **No `broadcastMessage` on the transport.** Because of per-player privacy projection, the host
  almost never sends identical bytes to everyone. Fan-out lives in the host's `PeerHub`.
- **`send` takes a whole message.** Fragmentation (needed for BLE) is a transport-internal
  concern, implemented natively so the JS bridge sees one event per message.
- **No accept/reject at transport level.** Approval is a protocol concern (`JOIN_PENDING`), so it
  behaves identically on every transport.
- **Events instead of callbacks per method**, so the host and client FSMs subscribe once.

### 6.3 Host runtime (`GameHost`)

- `PeerHub`: maps `peerId ↔ playerId`, tracks connection status, serializes sends per peer,
  drives heartbeats.
- `Lobby`: players, ready flags, host approvals, kick, settings; produces `LOBBY_STATE` messages.
- `ActionGate`: dedupes by `actionId`, checks the actor owns the seat, hands the action to the
  engine, turns `RuleViolation` into `ACTION_REJECTED`.
- `EventLog`: appends engine events with incrementing `stateVersion`; keeps a ring buffer of
  recent events for cheap catch-up.
- `PlayerViewProjector`: converts an engine event and state into what each recipient may see.
- `SessionRecovery`: reconnect tokens, disconnect grace timer, pause/resume.

### 6.4 Client runtime (`GameClient`)

Connection state machine:

```
Idle → Discovering → Connecting → Joining → InLobby → InGame → (Reconnecting ↔ InGame) → Left
                                         ↘ Rejected                       ↘ HostLost
```

It holds a `ClientGameView` (public state + own hand + `stateVersion`), applies events strictly
in order, asks for a snapshot on any gap, and exposes `legalMoves()` computed with the shared
engine rules so the UI can highlight playable cards with zero latency.

### 6.5 Lobby flow

1. Host taps Create Game, enters/keeps name, gets a `gameId` (UUID) and an optional 4-digit join
   code. Transport starts advertising.
2. Client taps Join Nearby Game, sees a list of games ("Ofir's Game · 3/8 · 🔒"), taps one.
3. Transport connects; client sends `JOIN_REQUEST { playerName, joinCode?, reconnect? }`.
4. Host replies `JOIN_ACCEPTED` (with the lobby snapshot), `JOIN_PENDING` (host approval
   required), or `JOIN_REJECTED` (full, wrong code, version mismatch, name taken).
5. Everyone receives `LOBBY_STATE` on each change. Clients toggle ready with `SET_READY`.
6. Host taps Start when ≥ 2 players and all non-host players are ready. Host stops advertising,
   engine deals, `GAME_EVENT`s flow.

### 6.6 Seats and bots

The host chooses the **seat count** (2–8, remembered between games, default 4). The advertisement
carries it as `maxPlayers`, the lobby shows `humans / seats`, and the host can change it while
the lobby is open, never below the humans already seated.

When the host taps **Start** with open seats, the host fills them with **bot players** and locks
the roster. Design rules:

- A bot is a seat like any other. The engine, the protocol and the other phones see a normal
  player with `kind: "bot"`; hands, turn order and rules are identical. Nothing in `src/game`
  knows what a bot is.
- Bots live only on the host, in `networking/host/bots/`. A `BotPlayer` owns a seat, receives
  the same `StateSnapshot` / `GAME_EVENT` stream a remote phone would, and submits ordinary
  `GAME_ACTION`s through the same `ActionGate`. The host validates bot moves exactly like human
  moves, so a bug in a bot can never corrupt the game.
- `BotStrategy` is an interface: `chooseAction(view: StateSnapshot, legal: LegalMoves): GameAction`.
  The MVP ships one heuristic strategy: prefer the colour you hold most of, keep wilds for
  last, play number cards before action cards, close a TAKI when no matching card remains, draw
  when nothing is playable. Difficulty levels are just other strategies.
- Bots act after a short randomised delay (roughly 0.6–1.4 s) so turns are readable, driven by a
  host-side scheduler that is paused whenever the session is paused.
- Nobody can join after Start (`REJECTED { reason: GAME_STARTED }`). If a human drops out
  mid-game, Phase 6 decides between waiting for a reconnect and handing the seat to a bot.

Phase 2 already implements the lobby half of this (seat count, LOBBY_STATE broadcasts, bot
fill-in at Start); the playing half arrives with the engine in Phases 3–4.

## 7. Message protocol

### 7.1 Envelope

```ts
export interface Envelope<T extends MessageType, P> {
  v: 1;              // protocol version
  t: T;              // MessageType
  id: string;        // unique message id (uuid) — used for de-duplication
  gid: string;       // gameId
  from: string;      // playerId, or 'host'
  ts: number;        // sender wall clock, informational only (never used for ordering)
  p: P;              // payload
}
```

Validated with zod on receipt on both sides. Unknown `t` or failed validation → message dropped
and logged; on the host it also counts against the peer (repeated garbage → disconnect).

### 7.2 Client → Host

| `t` | Payload | Notes |
|---|---|---|
| `JOIN_REQUEST` | `{ playerName, joinCode?, reconnect?: { playerId, token }, protocolVersion, appVersion }` | First message after connect |
| `SET_READY` | `{ ready: boolean }` | Lobby only |
| `LEAVE` | `{}` | Graceful exit |
| `GAME_ACTION` | `{ actionId, action: GameAction }` | See 7.4 |
| `RESYNC_REQUEST` | `{ knownVersion }` | Client detected a gap |
| `PING` | `{ nonce }` | Heartbeat, every 5 s |

`GameAction` (engine-level, discriminated union):

```ts
export enum GameActionType { PlayCard = 'PLAY_CARD', DrawCard = 'DRAW_CARD',
  ChooseColor = 'CHOOSE_COLOR', CloseTaki = 'CLOSE_TAKI' }

export type GameAction =
  | { type: GameActionType.PlayCard; cardId: string; chosenColor?: Color } // color optional shortcut for Change Color
  | { type: GameActionType.DrawCard }
  | { type: GameActionType.ChooseColor; color: Color }
  | { type: GameActionType.CloseTaki };
```

There is no separate `END_TURN`: in TAKI a turn ends automatically after a play or a draw. The
only explicit "I'm done" is `CLOSE_TAKI`, which ends an open TAKI sequence.

### 7.3 Host → Client

| `t` | Payload | Notes |
|---|---|---|
| `JOIN_ACCEPTED` | `{ playerId, reconnectToken, snapshot: StateSnapshot }` | Snapshot covers lobby or in-progress game |
| `JOIN_PENDING` | `{}` | Waiting for host approval |
| `JOIN_REJECTED` | `{ reason: JoinRejectReason }` | `FULL`, `BAD_CODE`, `VERSION_MISMATCH`, `NAME_TAKEN`, `DENIED`, `GAME_OVER` |
| `LOBBY_STATE` | `{ version, gameName, hostId, players: LobbyPlayer[], settings, joinCode? }` | Also sent while game is running (connected flags) |
| `GAME_EVENT` | `{ version, event: ClientGameEvent }` | Exactly one per `version` |
| `STATE_SNAPSHOT` | `StateSnapshot` | Full per-player view |
| `ACTION_REJECTED` | `{ actionId, reason: RuleViolationCode, message }` | Client rolls back optimistic UI if any |
| `KICKED` | `{ reason }` | |
| `HOST_CLOSING` | `{}` | Host ended the session |
| `PONG` | `{ nonce }` | |

### 7.4 Per-player view (privacy)

Full state lives only in `GameHost`. Every outbound message is produced by
`PlayerViewProjector.forPlayer(playerId)`:

```ts
export interface StateSnapshot {
  gameId: string;
  stateVersion: number;
  phase: ClientPhase;                     // see §9.2, redacted variant
  currentPlayerId: string;
  direction: 1 | -1;
  activeColor: Color | null;
  topCard: Card;
  drawPileCount: number;
  players: Array<{ id: string; name: string; cardCount: number; isHost: boolean;
                   connected: boolean; isReady: boolean; seat: number }>;
  you: { playerId: string; hand: Card[] };  // only the recipient's hand, ever
}
```

Engine events are redacted per recipient. Example: the engine emits
`CardsDrawn { playerId: 'p2', cards: [Red 4] }`. Player 2 receives that. Everyone else receives
`CardsDrawn { playerId: 'p2', count: 1 }`. The same applies to `HandDealt`. Public events
(`CardPlayed`, `ColorChosen`, `DirectionChanged`, `PlayerSkipped`, `TurnStarted`, `TakiOpened`,
`TakiClosed`, `DeckReshuffled`, `GameFinished`) are identical for all recipients.

The draw pile order and other players' hands never appear in any message.

### 7.5 Example exchange

```
B → A  GAME_ACTION  { actionId: "9f1c…", action: { type: "PLAY_CARD", cardId: "c_red_7_b" } }
A      engine.reduce(state, action, "p2")  → ok, events: [CardPlayed, TurnStarted]
A → *  GAME_EVENT   { version: 153, event: { type: "CARD_PLAYED", playerId: "p2", card: {...}, activeColor: "red" } }
A → *  GAME_EVENT   { version: 154, event: { type: "TURN_STARTED", playerId: "p3", phase: { kind: "AwaitingPlay" } } }

C → A  GAME_ACTION  { actionId: "22ab…", action: { type: "PLAY_CARD", cardId: "c_blue_2" } }   // wrong color
A → C  ACTION_REJECTED { actionId: "22ab…", reason: "CARD_DOES_NOT_MATCH", message: "Blue 2 cannot be played on Red 7" }
```

## 8. Game-state synchronization

### 8.1 Versioning

- The host's `EventLog` assigns `stateVersion = previous + 1` to every engine event. Lobby
  changes use the same counter so there is a single ordering.
- Each `GAME_EVENT` carries its `version`. A `STATE_SNAPSHOT` carries the version it reflects.
- Client rule: with `expected = lastApplied + 1`:
  - `version < expected` → duplicate, drop.
  - `version === expected` → apply, `lastApplied++`.
  - `version > expected` → gap; send `RESYNC_REQUEST { knownVersion }`, buffer nothing, wait.
- Host answer to a resync: a fresh `STATE_SNAPSHOT` for that player (always correct, under 2 KB).
  A later optimisation can replay events from the ring buffer when the gap is small.

Transports we use deliver in order per peer (Nearby `BYTES`, BLE ATT, TCP), so gaps only occur
across reconnects. The version check makes correctness independent of that assumption.

### 8.2 Idempotency and stale actions

- Every `GAME_ACTION` has a client-generated `actionId`. The host remembers the last N ids per
  player with their outcome; a duplicate gets the same reply and is not applied twice.
- Actions are validated against the current state, so a late `PLAY_CARD` after the turn moved
  on is rejected with `NOT_YOUR_TURN`. Clients never need to include a version, but may send
  `basedOnVersion` for better error messages.

### 8.3 Player disconnect and reconnect

1. Transport reports `peerDisconnected`, or 3 heartbeats are missed (about 15 s).
2. Host marks the seat `connected: false`, broadcasts `LOBBY_STATE`, and if it is that player's
   turn, pauses the game clock with a visible countdown (grace period, default 90 s).
3. Host re-advertises so the phone can find it again.
4. The client keeps `{ gameId, playerId, reconnectToken }` in AsyncStorage. On regaining the
   radio or returning from background it rediscovers the game by `gameId` and sends
   `JOIN_REQUEST { reconnect: { playerId, token } }`.
5. Host validates the token, rebinds the seat to the new `peerId`, replies `JOIN_ACCEPTED` with a
   full snapshot, broadcasts `connected: true`. Play resumes exactly where it stopped.
6. If the grace period expires the host may kick the seat (default) or auto-play "draw and pass"
   for that player each turn; this is a lobby setting.

The reconnect token is a random 128-bit value issued once per seat and never displayed.

### 8.4 Host disconnect and host migration

MVP behaviour: clients show "Connection to host lost, waiting…" and keep rediscovering by
`gameId` for the grace period. If the host app returns (it was backgrounded or the radio
blinked) everyone reconnects via §8.3 and the game continues, because the host also persists its
full state to AsyncStorage after every event.

Host migration proper is harder because only the host knows all hands. Phase 6 will evaluate a
"collaborative rebuild": the surviving player with the lowest seat number becomes host, asks each
client for its own hand and last known `stateVersion`, reconstructs the public state, and
reshuffles the unknown draw pile. It is acceptable for friendly play and it keeps hands private
from the other clients, but it trusts each client to report its own hand truthfully. I recommend
shipping the MVP without it and deciding later based on how often hosts actually drop.

### 8.5 Heartbeats and timeouts

- `PING`/`PONG` every 5 s per connection, on top of transport-level disconnect events.
- Connect timeout 15 s, join handshake timeout 10 s, resync timeout 5 s then retry.
- All timers live in the host/client runtimes, never in the engine.

### 8.6 App backgrounding

- Screen kept on during play, so backgrounding is mostly deliberate.
- Android client: the Nearby connection survives brief backgrounding; on `AppState` returning to
  `active` the client sends a `PING`, and if it times out, it runs the reconnect flow.
- Android host: the foreground service keeps it alive.

### 8.7 Persistence for recovery

AsyncStorage keys: `profile.playerName`, `settings.*`, `session.current`
(`{ gameId, playerId, reconnectToken, role, savedAt }`), and on the host `host.state.<gameId>`
(full engine state plus version). On launch, if a recent session exists, the Home screen offers
"Rejoin Ofir's Game".

## 9. Game engine design

### 9.1 Domain model (all in `src/game/`, pure TypeScript)

```ts
export enum Color { Red = 'red', Blue = 'blue', Green = 'green', Yellow = 'yellow' }
export enum CardKind { Number = 'number', Stop = 'stop', Plus = 'plus',
  ChangeDirection = 'change-direction', Taki = 'taki', ChangeColor = 'change-color' }

export type Card =
  | { id: string; kind: CardKind.Number; color: Color; value: 1 | 3 | 4 | 5 | 6 | 7 | 8 | 9 }
  | { id: string; kind: CardKind.Stop | CardKind.Plus | CardKind.ChangeDirection | CardKind.Taki; color: Color }
  | { id: string; kind: CardKind.ChangeColor };              // wild

export interface PlayerState { id: string; name: string; seat: number; hand: Card[] }

export interface GameState {
  gameId: string;
  rules: RuleSet;
  phase: GamePhase;
  players: PlayerState[];            // ordered by seat
  currentSeat: number;
  direction: 1 | -1;
  drawPile: Card[];
  discardPile: Card[];               // last element is the top card
  activeColor: Color | null;         // set by Change Color; otherwise the top card's color
  rng: RngState;                     // seeded PRNG so games and tests are reproducible
  version: number;
}
```

Engine API (pure functions):

```ts
reduce(state, action, actorId): Result<{ state: GameState; events: EngineEvent[] }, RuleViolation>
legalMoves(state, playerId): { playableCardIds: string[]; canDraw: boolean; canCloseTaki: boolean; mustChooseColor: boolean }
project(state, viewerId): StateSnapshot
createGame(players, rules, seed): GameState
```

### 9.2 State machine

```ts
export type GamePhase =
  | { kind: 'AwaitingPlay'; playerId: string; afterPlus: boolean }   // normal turn; afterPlus = must play again
  | { kind: 'TakiSequence'; playerId: string; color: Color; playedCount: number; lastCardId: string }
  | { kind: 'AwaitingColorChoice'; playerId: string }
  | { kind: 'Finished'; winnerId: string; finishOrder: string[] };
```

As built in Phase 3: "Lobby" and "Starting" are session phases (`LobbyPhase` in the protocol),
not engine phases; a `GameState` only exists once cards are dealt. Every successful action ends
with a `PhaseChanged` event carrying the new phase, current player and direction, so a client can
track whose turn it is from events alone and only needs a snapshot after a gap.

Transitions (MVP rule set):

| From | Action | Guard | To |
|---|---|---|---|
| `AwaitingPlay` | `PlayCard` (number) | matches color or value | next player, `AwaitingPlay` |
| `AwaitingPlay` | `PlayCard` (Stop) | matches color or kind | skip one, `AwaitingPlay` |
| `AwaitingPlay` | `PlayCard` (Plus) | matches | same player, `AwaitingPlay { afterPlus: true }` |
| `AwaitingPlay` | `PlayCard` (Change Direction) | matches | reverse; next player (2 players: same player) |
| `AwaitingPlay` | `PlayCard` (TAKI) | matches | `TakiSequence { color }` |
| `AwaitingPlay` | `PlayCard` (Change Color) | always | `AwaitingColorChoice`, or straight to next player if `chosenColor` was supplied |
| `AwaitingPlay` | `DrawCard` | always (reshuffle if needed) | next player; if `afterPlus`, turn ends after the draw |
| `TakiSequence` | `PlayCard` | same color as sequence | stay, `playedCount + 1` |
| `TakiSequence` | `CloseTaki` | always | apply the *last* card's effect, then advance |
| `AwaitingColorChoice` | `ChooseColor` | valid color | set `activeColor`, advance |
| any play | — | hand empty and last card may end the game | `Finished` |

"Pause because a player disconnected" is **not** an engine phase; it is a session status held by
the host runtime. The engine stays deterministic and testable.

### 9.3 Rule/handler architecture

```ts
export interface CardEffectHandler {
  readonly kind: CardKind;
  /** Extra playability beyond the shared matching rule, e.g. wild cards. */
  isPlayable(card: Card, ctx: PlayContext): boolean;
  /** Called when the card takes effect (immediately, or when a TAKI sequence closes). */
  apply(card: Card, ctx: PlayContext): EffectOutcome;   // { events, nextPhaseHint }
}
```

- `MatchingRule` (shared): same color as `activeColor`, same number, or same kind.
- One handler per `CardKind`, registered in a `CardHandlerRegistry`. Adding "Plus 2", "Super
  TAKI", "King" or "Break Plus Three" later means: a new `CardKind`, its deck entries, and one
  handler. No UI or networking change.
- `RuleSet` holds house-rule toggles: `cannotFinishOnPlus` (default true), `twoPlayerReverseActsAsStop`
  (default true), `drawnCardEndsTurn` (default true), `initialHandSize` (8), `maxPlayers` (8).
- `RuleViolation` codes: `NOT_YOUR_TURN`, `CARD_NOT_IN_HAND`, `CARD_DOES_NOT_MATCH`,
  `TAKI_COLOR_MISMATCH`, `MUST_CHOOSE_COLOR`, `INVALID_PHASE`, `GAME_FINISHED`.

### 9.4 Deck (MVP)

Two copies of each: numbers 1, 3–9 in four colors (64), Stop / Plus / Change Direction / TAKI in
four colors (32), plus four Change Color wilds. 100 cards, built by `DeckBuilder(rules)`. The
first face-up card is the first number card from the shuffled pile. When the draw pile empties,
the discard pile minus its top card is reshuffled; if nothing remains, drawing is a no-op and the
turn passes.

## 12. Security for the MVP

- **Game id**: UUID v4 generated per game; join requests must quote it.
- **Join code**: optional 4-digit code shown in the host lobby, checked in `JOIN_REQUEST`.
- **Host approval**: optional lobby setting; joiners sit in `JOIN_PENDING` until the host taps
  Accept.
- **Transport protections**: Nearby Connections encrypts the link and provides an
  authentication token (we display it as a verification code). Multipeer offers
  `encryptionPreference = .required`. Plain BLE GATT without bonding is **not** encrypted; when
  we build it we should add an application-layer X25519 key agreement on join and
  ChaCha20-Poly1305 per session (about 50 lines with libsodium). Deferred, as agreed.
- **Authority**: clients can only send actions; the host validates everything against its own
  state, so a modified client can at worst play legal moves for itself.
- **Privacy**: per-player projection (§7.4). Hands and deck order never leave the host.
